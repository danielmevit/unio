### Added
- Truthful selection, effort and final-response handling for the Vibe 3.1.1 route of the optional Mistral Vibe adapter, without changing 2.26.1 behavior. The per-session selection is now verified only from what the owned invocation actually selected: a bounded no-follow read of `session/meta.json` under the output directory first, then the export config's per-session section and `active_model`. `routed_model_config`/`routed_default_model` are treated as the account's DEFAULT declaration: used for the selection only when they name the selected alias, and otherwise preserved as separate `routed_default_*` fields, so the real captured GLM session (selected glm-5-3 / wire zai-glm-5-3 against a routed default Mistral Large 4) is recorded as verified with the contradicting default preserved instead of a false mismatch.
### Changed
- Partial, catalog-only or default-only identity metadata can no longer produce a verified selection: verification now requires an actual selected alias and wire name, and thinking-only metadata stays `unknown`. Effort provenance is separate from identity: only a declaration attributable to the selected model is recorded as the session thinking; missing effort metadata is unknown and is never proof that the requested level took effect (effective model/effort remain Unknown on every version).
- The 3.1.1 `--output json` message-list parser accepts the validated real assistant content forms (plain string and typed text blocks), so real final replies record non-zero text bytes with exact content-form-tagged SHA-256 provenance. A history ending in a tool-call-only assistant entry or an empty final acknowledgment is recorded as `final_without_text` — never selected from an earlier acknowledgment and never proof of a completed required delivery; the CLI exit, export verdict, required artifacts and acceptance stay separate.
- On 3.1.1 there is no real per-run thinking control (the `VIBE_*` overlay is 2.26.1-only and no native thinking flag exists), so `--thinking low|medium` is now refused before any provider invocation with an actionable message instead of silently executing the account's existing high level. Only `high` runs — matching the catalog declaration observed for the validated aliases — with the effective effort recorded as unknown. The 2.26.1 overlay keeps all three levels, and the offline route-contract preflight keeps accepting the union exactly as it does for cap choices, so dispatch and execution agree. The retained numeric ceilings (16M tokens/$10/180 turns/120 minutes) are adapter policy, not provider limits.
