# Incremental application audits

Audit one concrete flow per assignment, with a pinned revision and explicit
coverage. A useful default for a frontier-model research pass is20–30minutes;
use longer bounds when the dependencies justify them. Keep reasoning effort
separate from the pass duration and subscription coordination tier.

Begin by writing a substantive module assessment within the first few minutes.
Update findings, coverage and the next step after each concrete result and
before long checks. Record host timestamps, exact source locations, confidence,
actual reproduction commands and exits. Separate confirmed defects, static
concerns, hypotheses and design suggestions. Partial coverage is not a whole-
application verdict.

Carry a lean packet of relevant previous findings and source pointers into the
next pass. Reuse native session history when needed, preserving the original
session and failures. Avoid repeating the complete installer and broad inventory
by default. Keep all audit files in the declared delivery location and retain
local checkpoints independently of the final response.

Smaller scope improves the chance of completing a useful section before a
cutoff; total token savings require measurement, and repeated setup can increase
cost. It cannot bypass a hard provider account limit. Preserve real quota exits,
missing delivery and Unknown values; never switch models, credentials, billing
or paid fallback silently. Current project and owner routing rules prevail.

A lead validates claims before assigning fixes. An architectural preference is
not a release blocker by itself. Preserve strict ownership and safety controls;
read their dependencies and tests before declaring them unnecessary. Keep the
independent current-code review and final lead assessment required by the project.
