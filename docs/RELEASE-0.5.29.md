# Unio 0.5.29 — clearer setup and reusable launch recipes

Unreleased candidate. All source tasks have native validation evidence; current
independent source reviews, lead composition assessment and the single full
combined quality gate are still required. Official publication and installation
are separate steps. Check the official tag/assets and actual receipts before
claiming delivery.

## Practical changes

A reusable route profile declares the requested Vibe CLI/model/thinking settings,
receipt destination and per-run caps. `unio routes` lists profiles, `show` describes
one and `compile` prints one safely quoted existing `agents.conf` line. You choose
whether to add that line, map its real shared account and start a normal task.
No provider runs and no configuration changes just to inspect or compile.

V1 supports the tested packaged Vibe3.1.1/GLM5.3 path. See the
[profile guide](integrations/ROUTE-PROFILES.md). It retains legacy route commands,
uses the trusted adapter's argument bounds, rejects malformed/unsupported input,
and handles native alias-prefix and physical-line constraints explicitly.

Fresh lead templates use neutral owner wording and supported score/experience
commands, and select CodeGraph only when the repository is already indexed.
Existing custom MASTER templates and project routers are preserved. The tier
table correctly calls two workflows `medium`; `balanced` is a work mode.

Recognized Vibe native setup errors now receive a bounded typed reason and a
fixed operator line, including an allowlisted unavailable alias or rejected flag.
The implementation recognizes the preserved real unavailable-model failure.
Untrusted error text and available-model lists are not copied into that hint.

## Limits and unchanged boundaries

Profiles describe requested settings, not proven effective model/effort, remaining
allowance or model availability. Compilation does not prove a worker can start,
validate a subscription, install/update a CLI or change native account groups.
Map aliases that share an account to the real shared group before dispatch.
Other providers/versions/wrapped commands keep the existing legacy interface.
This is a compiler foundation, not automatic profile-driven dispatch or lab-aware
review eligibility. It makes no measured token-saving/performance claim.

Existing template contents are not silently migrated. The remaining historical
fleet/scoreboard guidance is a separate neutral-defaults task. Legal credit stays.
No new retry, quota bypass, paid fallback, whole-install atomicity or OS sandbox
is introduced. Setup hints never change actual exits, usage Unknowns, policy,
bench state, current validation/review freshness or human acceptance.

No save-integrity checks, benchmark evidence, recovery data, native ownership or
worker-account protections are removed. Save cost requires current measurements
before selecting an optimization. No dashboard/website redesign or desktop/phone
feature is included.

## Following priorities

Extend existing native evidence rather than creating a second review system:
precisely bind external report-only reviews and ordinary-task acceptance, preview
inherited task scope before provider launch, and separate current owner policy
from neutral defaults. Then investigate current save-cap/latency costs without
deleting evidence, and extract one engine module at a time. Managed lead, phone,
Windows and macOS remain later milestones.
